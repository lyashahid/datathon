# UI and policy workflow redesign

This records the first UI redesign against the supplied backend. Passenger, resident, timetable, cost, live-context and Vela capabilities were subsequently added; see [policy-expansion.md](policy-expansion.md) for the current workspaces and verification.

## References inspected

The design assessment uses the actual artwork in Dwinawan/Paperpillar's [Finance Data Charts exploration](https://dribbble.com/shots/24061999--Exploration-Finance-Data-Charts), the original `MobilityWorkspace.svelte` and `PlanningAtlas.svelte` preserved in `D:\Projects\Personal\datathon-backup-20261014-124331`, and the backup's product screenshots.

The finance reference uses a pale lavender background, white rounded cards, restrained shadows, prominent metrics and smaller secondary labels. Green and purple grouped bars, pastel category circles, and compact progress displays make each card readable on its own. Card heights vary with the amount of information, and small report actions sit alongside titles. For this project, the transferable idea is a calm, modular overview of real inventory, accessibility and evidence coverage. The supplied backend does not provide passenger histories or forecast time series.

The original map fills the workspace, with a compact task control at the top, contextual selection information, and intervention tools near the bottom. Its application shell preserves query context between pages, keeps the map mounted, and passes selected locations and planning context between analytics, decisions and the editor. Those behaviors provide continuity: an analytical finding can become a location to inspect, then a proposal to test.

## Decision journey

| Destination   | Policy question                                                     | Primary next action                                                                                      |
| ------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Overview      | What should I investigate, and how complete is the evidence?        | Select an island or priority and open its planning map.                                                  |
| Planning map  | Where are the facilities, connections and gaps for this island?     | Inspect a record, check a route, or begin a proposal in the same island context.                         |
| Proposals     | What change could I test, and what did the backend actually change? | Edit an option or start from a recommendation, simulate, compare against a named reference, then export. |
| Live movement | What optional movements are currently observed?                     | Enable a bounded refresh, inspect provider coverage, then pause.                                         |
| Evidence      | What supports this result, and what remains unknown?                | Inspect source matching, model boundaries and missing capabilities, then return to the relevant task.    |

Recommendations belong within Proposals as assisted starting points. They do not require a competing global destination. The map belongs in the Planning map destination rather than occupying space beside every analytics or evidence view.

The shared state should retain the selected island, proposal draft, comparison reference and valid results across navigation. A new island selection clears inappropriate route/results and makes any retained proposal's scope visible. Overview-to-map and map-to-proposal actions must preserve the exact island identity; a similarly named island is not an acceptable substitute. Local persistence should be described as a browser draft, since the backend does not expose a saved-proposal database.

## Interaction requirements

- The overview should combine backend-derived metric cards, meaningful source-backed charts and an actionable island table. Missing records and scores affected by missing evidence need explicit labels.
- The map should keep inspection, route picking and proposal placement as distinct modes, with one active mode at a time, clear instructions, cancel/Escape, and contextual details. The selected feature and its source quality should remain easy to inspect.
- Proposal editing should prioritize ordinary interventions and place graph-node/edge identifiers and other specialist fields behind a clearly named advanced section. Empty, loading, validation, unapplied-operation and comparison states should describe the next useful action.
- Controls use the installed shadcn-svelte buttons, inputs, native selectors, tabs, sheets, cards, labels and badges. The tab triggers have associated content panels. Semantic HTML remains appropriate for data tables and inline status/error messages. Keyboard focus and selected states should remain visible.
- Responsive navigation should expose every destination. At narrow widths, island selection and contextual map details should use bounded sheets/panels; chart axes, controls, attribution and map legends must remain readable and avoid overlap.

## Implementation review

| Before                                                                 | After                                                                                                                             | Why                                                                                                   |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| The map shared space with most workflows.                              | Overview and Evidence have dedicated pages; Planning map, Proposals and Live movement retain the atlas.                           | Each destination answers one policy question while preserving place context.                          |
| A separate recommendations destination competed with scenario editing. | Proposals contains Build option, Find candidates and Review results.                                                              | A recommendation becomes a draft to inspect, test and compare in one journey.                         |
| National counts were presented as a compact inventory strip.           | Source-backed facility bars, category proportions, coordinate coverage, accessibility distribution and a searchable island table. | Decision makers can screen the country, filter the evidence and choose an exact place to investigate. |
| Map controls and proposal fields were continuously exposed.            | An island-search sheet, layer/view controls, contextual route tools and advanced coordinate/graph sections.                       | The next useful action remains prominent without losing specialist controls.                          |
| Results and source limits were scattered.                              | Explicit review panels, named references, decision-brief exports and a source-family Evidence page.                               | A proposal can be shared alongside its actual modeled changes and limitations.                        |

The overview's national facility total includes unassigned official records; geographic comparisons use island-linked records. Coordinate coverage measures geometry availability, including provisional matches. Accessibility is an unweighted cached island index, not a population-weighted outcome or a forecast. The interface makes these distinctions visible rather than adding models missing from the supplied backend.

The selected island and proposal subview are represented in the URL. Browser navigation restores those values. A browser draft persists through reload; proposal results and comparison references persist during navigation in the current session. The map mounts on first use and is retained thereafter, while analytics stays mounted to preserve filters and avoid repeated analysis downloads.
